# Building Your Own Software Factory — Eric Zakariasson (Cursor)

**Author:** Eric Zakariasson — engineer at Cursor working on developer experience and product
**Venue:** AI Engineer (conference talk, ~30 min talk + extended Q&A)
**URL:** https://www.youtube.com/watch?v=rnDm57Py54A
**Pillar:** [[software-factory]] / [[agent-harness]]

## Summary

A practitioner's tour of how Cursor is building toward a software factory by dogfooding its own product. Zakariasson opens by anchoring on [[five-levels-shapiro|Dan Shapiro's five levels of autonomy]] (citing the January–February 2026 blog post), placing himself personally at **Level 4** for most of his work and Cursor as a company "not really there yet" but with sub-parts running fairly autonomously. He motivates the factory metaphor with three reasons: throughput (agents run 24/7 with no sleep/food constraint), consistency (assembly lines produce uniform output if guardrails are right), and leverage of human taste/creativity rather than waiting for humans to type.

The structural core of the talk is a three-part decomposition for **building** a factory: **primitives & patterns**, **guardrails**, and **enablers**. Primitives = how the codebase is structured (modular, co-located, with discoverable folders so the agent can `ls` instead of grepping the whole repo) plus existing usage patterns (auth methods, startup scripts, test patterns) the agent can copy. Guardrails = rules, hooks (e.g., block the agent from touching encryption/auth code), and tests. Enablers = skills, MCPs, environment access — what the agent is allowed to *do*. He summarizes this as a checklist: **runnable, accessible, verifiable** — and singles out verifiable systems as where teams should spend more time, because backend invariants are easy and UI verification is genuinely hard. His sharpest contrarian claim is on rules: **"rules should emerge dynamically"** — *not* "install every rule from cursor.directory." Models follow instructions well enough now that rules are most useful as captured corrections of past failures, not pre-emptive scaffolding.

The demo segment shows Cursor 3 (a complete rewrite with no VS Code base, launched "a couple weeks ago" — agent-first UI, no traditional file sidebar) running an Ableton-style music-production web app he built without ever writing code himself. The agent reads `package.json`, runs the dev server, and uses Playwright e2e tests as its self-verification harness. He then shows updated cloud agents — each gets its own VM, and a computer-use tool lets the agent record a video of itself clicking around to validate a UI change (his cited "AGI moment" from the internal launch). He notes Cursor is running "multiple thousands a day" of cloud agents internally.

The **running** the factory section is the mindset shift: worker → manager, sync → async. He argues there is **no shortcut** here — "just spawn a shitload of agents and let them do the work." On environment isolation he prefers full VMs over git worktrees: shared workspaces force you to branch databases/caches/user-state anyway, and isolation lets you scale to thousands of parallel agents. The **scaling** section showcases automations Cursor uses internally: a **daily review** (Slack + GitHub summary), a **read-merge-PR-comments** loop that stores human review feedback for future agents to learn from, an **agentic code owner** that assesses PR risk and either auto-approves low-risk PRs (unblocking engineers) or pulls in the original code-author for high-risk ones, and a **continual learning** plugin that extracts rules from chat-history transcripts so users don't have to remember to write rules manually. He ends with five takeaways: be clear about intent; don't outsource important decisions (security, payments, auth); build tools and systems; store context (transcripts, artifacts) for later; and **let agents be free** — citing a Lovable colleague's "vent tool" that became signal for capability gaps when the agent started complaining about not being able to read images.

The Q&A is unusually substantive and runs as long as the talk. It covers code quality (humans have the same architectural-drift problem, just slower; "more architectural review for humans" is the answer), team-level rule fragmentation as a cultural problem, brownfield/enterprise mission-critical systems (spend compute up-front, security-sentinel automations running 10 checks on critical PRs, use AI for quality not just velocity), the gap between rules and continual-learning weight updates ("hacky plugin" vs. true per-team fine-tuning), GUI/user-acceptance testing via computer-use, prototype-to-production handoff (don't migrate prototypes — rewrite them; PMs hand off cloud-agent links as "interactive Figma"), brownouts/blackouts as a new operational risk, daily workflow (5–10 cloud agents in parallel, sync planning → async execution), file/factory organization ("somewhat unsolved" — Cursor 3 is the first stab at multi-agent orchestration UI), team archetypes (PMs, designers who are 50/50 Figma/code and push to prod, engineers, data scientists), Linear integration (every ticket spawns a cloud agent; stale feature flags auto-create issues that auto-remove the flag), the just-launched **Cursor Workers** (self-hosted infrastructure that runs the same agent harness on a Mac mini or any VM), and detecting wasted agents (instrumentation Cursor "could do better" on).

## Key Claims

- **Personally at Level 4** ([[five-levels-shapiro|Shapiro framework]]) — delegates as much work as possible to agents, reviews outputs before code, "still looks at the code sometimes."
- **Cursor as a company is not yet a factory** — sub-parts run autonomously, but real factories require assembly lines, observability, managers, and a lot of work the software industry is borrowing from manufacturing.
- **Three reasons to build a factory**: (1) throughput — agents run 24/7; (2) consistency — assembly lines produce uniform output if guardrails are right; (3) leverage human taste/creativity instead of waiting for human typing speed.
- **The three-part build decomposition** — primitives & patterns / guardrails / enablers. Maps cleanly onto [[skill-issue-harness-engineering|Kyle's six harness levers]] but reorganized around what the agent *needs* (structure), what *bounds* it (rules/hooks/tests), and what *empowers* it (skills/MCPs/environment).
- **Three-word checklist: runnable, accessible, verifiable.** Verifiable is the under-invested one. Backend invariants are easy; UI verification ("does the button have a loading spinner?") is genuinely hard and requires computer-use or similar.
- **Rules should emerge dynamically** — *contra* the "install every rule from cursor.directory" approach. Capture corrections of observed failures; don't pre-emptively scaffold. As models improve at instruction-following, fewer rules are needed.
- **Specific guardrail example: hooks blocking agents from touching auth/encryption/sensitive code** where mistakes are "very, very, very costly."
- **Cursor 3** — complete rewrite, no VS Code base, agent-first UI streamlined for managing many agents instead of editing files. Launched "a couple weeks ago" (≈ April 2026 from the May 2026 talk). Designed because the team needed a "control panel" for agents.
- **Cloud agents with computer use** — each agent gets its own VM, can spawn the cursor app + ClickHouse + Postgres + Redis, and uses a computer-use tool to record video of itself clicking around to verify UI changes. Approximate cost: **~$1/turn** for one cloud-agent turn.
- **"Multiple thousands a day"** of cloud agents running internally at Cursor.
- **Isolated VMs > shared-workspace worktrees** for parallel agents — shared workspaces force you to branch DB/cache/user-state anyway, so just go full VM and scale to hundreds/thousands.
- **Spawn-a-shitload-of-agents has no shortcut.** The mindset shift to manager-of-agents requires actually running the experiment; no theoretical workaround.
- **Frontload context, then go async.** Send long specs/plans up front; once you're aligned with the model's strengths/weaknesses you give shorter prompts.
- **Cursor's internal automations**:
    - **Daily review** — Slack + GitHub summary of what the user did today, replacing manual notes.
    - **Read-merge-PR-comments** — stores human review feedback as agent-learnable signal ("if a human bothered to comment, it's high signal").
    - **Agentic code owner** — assesses PR risk; low-risk → auto-approve (unblocks engineers); high-risk → pulls in the original author. Solved real bottleneck where human code-owners were "right 80% of the time but blocked us 20%."
    - **Continual learning plugin** — extracts rules from chat-history transcripts so you don't have to remember to write rules. Also runs on every Linear ticket via first-party integration.
- **Lovable's "vent tool" anecdote** — a colleague gave the agent a tool to post complaints to Slack as a joke; turned into capability-gap signal when the agent complained it couldn't read images. Argues for **letting agents be free** — give them a way to surface what they're missing.
- **Rules as the human↔model bridge** — Cursor doesn't use foreign keys for performance reasons, but models always add them. Bugbot has a rule that flags this. The rule isn't pre-emptive scaffolding; it's the captured gap between model default and team intent.
- **Cursor Workers** — announced "yesterday" relative to the talk (May 2026). Self-hosted agent harness; same orchestration as cloud agents but runs on any machine (Mac mini, VM, dev container). Accessed via `agent worker start` CLI command and surfaces in cursor cloud as a self-hosted worker. Closes the loop for users who don't want managed cloud agents.
- **Linear-driven autonomous loops** — every Linear ticket spawns a cloud agent. Stale feature flags auto-create Linear issues that trigger auto-removal cloud agents — a fully autonomous closed loop signal → ticket → PR → merge.
- **Daily workflow: 5–10 cloud agents in parallel.** Sync planning (specs in cursor, sourcing notion/slack) → async execution (cloud agents) → review/merge. Context switching across 4+ repos/areas is "the sad reality."
- **Multi-agent orchestration UI is "somewhat unsolved."** Cursor 3 is "the first stab" — nested sub-agents, project views, aggregated status. Spec stored as markdown folders checked into the codebase, agent-readable.
- **Team archetypes at Cursor**: PMs (talk to GTM/sales/users/engineers, manage and shield), **designers (50/50 Figma/code, push to production)**, engineers, data scientists/analysts. Teams are **domain-modular** (extensibility team, cloud team) — Conway's Law avoidance.
- **Enterprise/security pattern: spend tokens up front.** Manually written tests for critical systems + automations like the security team's "Security Sentinel" (10 invariant checks on certain PRs). One audience member calls this "use AI to focus on quality, not velocity" and Eric strongly agrees: "if you trust the tests, you trust the output even though you don't have to look at the code."
- **Architectural drift is a real problem and the answer is more human architectural review.** Models have completion bias; existing references partially mitigate, but humans must scope and plan architecture.
- **Brownouts/blackouts as a new operational risk** — humans remain accountable; observability and monitoring matter; some critical lines may need to be human-written or human-reviewed always.
- **Anti-pattern: prototype migration.** Don't try to migrate a vibe-coded prototype to production — rewrite. PMs hand off prototypes as cloud-agent links ("interactive Figma") or HTML mega-files in a `prototypes` repo.
- **Future of model rules: true continual learning at the weights level.** Current rule plugins are "hacky"; eventual goal is per-team fine-tuning that bakes preferences into the model.

## Questions Raised

- **Is "rules should emerge dynamically" durable?** Eric's stance is contingent on improving instruction-following. If models plateau, pre-emptive scaffolding (cursor.directory style) might come back. Worth tracking.
- **Cost trajectory at the factory scale.** ~$1/cloud-agent-turn × thousands/day = real money even at Cursor's scale. What happens to factory economics at smaller orgs without Anysphere-tier model deals?
- **Self-hosted Cursor Workers** — does this materially shift the build-vs-buy calculation for enterprises? Same harness on owned infrastructure may resolve the brownout/security objections raised in Q&A.
- **Multi-agent orchestration UI** — Eric admits Cursor 3 is "the first stab" and the problem is "somewhat unsolved." How does this evolve? What does the manager-of-managers UI look like at 100+ agents?
- **Architectural review as the new bottleneck.** Eric explicitly says "more architectural review for humans" is the answer to drift. Is there an automation for *that*? Or is system design the durable human moat?
- **Domain-modular team structure.** Cursor's "extensibility team" / "cloud team" / etc. is Conway's Law applied to factory architecture. Is this generalizable, or specific to Cursor building a developer product?
- **Prototype-to-production rewrites at scale.** Eric's "don't migrate, rewrite" is operationally tractable for a 100-person company. At enterprise scale with 10k engineers and shared infrastructure, is rewrite-from-prototype workable? StrongDM's three-person team suggests yes for greenfield; brownfield mission-critical (the Q&A questioner) is unresolved.
- **The agentic-code-owner pattern's failure modes.** Eric mentions misconfigured code owners as a previous problem; what failure modes does the *agentic* version introduce? When does auto-approve go wrong?
- **Vent-tool as a category.** Lovable's vent-tool anecdote suggests a general pattern: instrument agents to surface their own complaints. Is this a missing primitive in agent harnesses?
